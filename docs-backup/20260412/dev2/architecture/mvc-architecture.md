# PiliNote MVC架构设计

## 架构概述

基于bilitool的MVC架构设计理念，PiliNote采用分层架构设计，确保代码的可维护性、可扩展性和可测试性。

## 层次职责

### View层（表现层）
**职责**：用户界面展示和用户交互
- 处理用户输入和显示逻辑
- 状态管理（Zustand）
- 路由导航
- API调用（通过服务层）

### Controller层（控制层）
**职责**：请求处理和业务逻辑编排
- 接收HTTP请求
- 参数验证和错误处理
- 调用Service层处理业务逻辑
- 返回标准化响应

### Service层（服务层）
**职责**：业务逻辑实现
- B站API集成
- 下载任务管理
- 文件处理
- 数据转换

### Model层（数据层）
**职责**：数据持久化和数据定义
- 数据库模型定义
- 数据验证（Pydantic）
- 数据库操作
- 配置管理

### Utility层（工具层）
**职责**：通用工具函数
- 加密解密
- 数据验证
- 日志记录
- 格式化转换

## 数据流向

### 请求流程
```
用户操作 → View层 → HTTP请求 → Controller层 → Service层 → Model层 → 数据库/外部API
                                                    ↓
                                                响应数据
                                                    ↓
用户界面 ← View层 ← HTTP响应 ← Controller层 ← Service层 ← Model层 ← 数据处理结果
```

### 示例：用户登录流程
1. **View层**: 用户在LoginPage输入SESSDATA
2. **Controller层**: auth.py路由接收POST /api/auth/sessdata
3. **Service层**: BilibiliService.login_by_sessdata处理登录
4. **Model层**: 保存用户信息到数据库
5. **响应**: 返回用户信息和认证状态
6. **View层**: 更新Zustand store，跳转到HomePage

## 设计原则

### 1. 单一职责
- 每层只负责自己的职责
- Model只负责数据，不包含业务逻辑
- View只负责展示，不包含业务逻辑
- Controller只负责协调，不包含具体实现

### 2. 依赖注入
- Controller通过依赖注入使用Service
- Service通过依赖注入使用Model
- 便于测试和替换实现

### 3. 接口抽象
- Service层提供统一的接口
- 便于替换底层实现
- 支持多种存储方式（SQLite/PostgreSQL）

### 4. 错误处理
- Controller层统一错误处理
- Service层抛出业务异常
- Model层数据验证异常

## 扩展性设计

### 添加新功能模块
1. 在Service层创建新的服务模块
2. 在Controller层创建对应的控制器
3. 在Model层创建数据模型和模式
4. 在View层创建UI组件
5. 注册新的路由

### 添加新的数据源
1. 在Service层创建新的服务模块
2. 实现统一的服务接口
3. 在Controller层使用新服务
4. 无需修改View层代码

## 技术选型理由

### 为什么选择MVC架构
- **分层清晰**: 便于团队协作和维护
- **职责分离**: 易于测试和调试
- **可扩展性**: 新功能易于添加
- **可维护性**: 代码结构清晰

### 为什么选择这些技术栈
- **FastAPI**: 现代化、高性能、自动文档
- **React 19**: 组件化、生态丰富、性能优秀
- **Zustand**: 轻量级、简单易用
- **SQLAlchemy**: 成熟ORM、支持多种数据库
- **yt-dlp**: 功能强大的下载工具
