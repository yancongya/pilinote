# bili-sync 架构设计

## 核心概念

### B 站视频结构

bili-sync 采用了三层层级结构来组织 B 站内容：

```
Video Source (视频源)
    └── Video (视频)
        └── Page (分页)
```

**Video Source**：视频源的抽象概念，包括：
- 收藏夹 (Favorite)
- 稍后再看 (Watch Later)
- 视频合集/列表 (Collection)
- UP 主投稿 (Submission)

**Video**：独立的视频单元，包含：
- 唯一的 bvid
- 封面、描述、标签
- 一个或多个分页

**Page**：视频的分页单元，包含：
- 唯一的 cid
- 封面、视频、音频、弹幕

### 重要区别：视频合集 vs 多页视频

这是一个容易混淆的概念：

- **视频合集**：由多个**仅包含单个 page 的 video** 组成的 video source
- **多页视频**：由多个 page 组成的单个 video

两者处于不同层级，处理方式完全不同。

## 数据库设计

### 数据模型

采用非交叉的层级结构设计，不考虑单个 video 被多个 video source 引用的情况。

#### Video Source 表

采用多表设计，每种 video source 都有独立的表：
- `favorite` - 收藏夹
- `watch_later` - 稍后再看
- `collection` - 视频合集/列表
- `submission` - UP 主投稿

#### Video 表

包含 video 的基本信息：
- bvid、标题、封面、描述、标签
- 与 video source 的关联
- 每种 video source 都有对应的外键列（favorite_id, collection_id 等）
- 使用 `(video_source_id, bvid)` 建立唯一索引

#### Page 表

包含 page 的基本信息：
- cid、标题、封面
- 与 video 的关联

## 与媒体服务器的映射

### 文件结构设计

#### 单页视频
```
{video_name}/
├── {page_name}.mp4
├── {page_name}.nfo
└── {page_name}-poster.jpg
```

#### 多页视频
```
{video_name}/
├── poster.jpg
├── Season 1/
│   ├── {page_name} - S01E01.mp4
│   ├── {page_name} - S01E01.nfo
│   ├── {page_name} - S01E01-thumb.jpg
│   ├── {page_name} - S01E02.mp4
│   ├── {page_name} - S01E02.nfo
│   └── {page_name} - S01E02-thumb.jpg
└── tvshow.nfo
```

### Emby/Jellyfin 对应关系

- **文件夹** → video source
- **电视剧** → video
- **第一季的所有分集** → page

**注意**：单 page 的 video 会展开到第二层级，成为与电视剧同级的电影。

**重要**：需要将媒体库类型设置为"混合内容"以支持同时显示电视剧与电影。

## 程序执行流程

### 1. 初始化阶段

- 读取配置文件
- 迁移数据库
- 初始化日志系统
- 自动创建不存在的必要文件

### 2. 扫描 Video Source

**目标**：获取新视频的简单信息并填充到数据库

**关键优化**：避免频繁的全量扫描

**实现机制**：
- 每个 video source 有 `latest_row_at` 列记录处理过的最新视频时间
- 请求时按时间排序，新视频在前
- 排序依据：收藏夹按收藏时间，投稿按投稿时间
- 逐页请求，直到遇到 `<= latest_row_at` 的视频停止
- 更新 `latest_row_at` 为最新的视频时间

**注意事项**：
- B 站接口为了节省资源，返回的视频列表通常是分页的
- 列表中的视频信息是简化的，不包含完整详情

### 3. 填充 Video 详情

**目标**：为新增视频填充详细信息

**实现机制**：
- 筛选出所有未完全填充信息的 video
- 逐个获取视频详细信息（标签、包含的 page 等）
- 遇到 -404 错误码时，标记视频为无效并跳过

**填充的信息包括**：
- 视频标签
- 分页列表
- 视频元数据

### 4. 下载未处理的视频

**目标**：下载所有符合条件的视频

**筛选条件**：
- 未完全下载
- 成功填充详细信息

**并发控制**：
- video 层级：最多 3 个任务同时下载
- page 层级：最多 2 个任务同时下载

**下载状态管理**：
- 使用 `status` 字段标记下载状态
- status 的不同位表示不同部分（封面、视频、nfo 等）
- 根据位状态决定是否需要下载

**重试机制**：
- 失败次数记录在 status 字段中
- 下次下载时自动重试
- 超过阈值后标记为下载失败，后续忽略

**风控处理**：
- 检测到风控时，不认为是单个视频失败
- 终止整个 video source 的下载任务
- 等待下次扫描时重试

## 并发模型

### 多级并发

```
Video Source 级别（串行处理每个 source）
    └── Video 级别（并发，最多 3 个）
        └── Page 级别（并发，最多 2 个）
            └── 分块下载（并发，默认 4 个块）
```

### 并发控制

**请求频率限制**：
- 使用漏桶算法
- 针对主站 API 请求（视频列表、视频信息、流地址等）
- 不限制实际的视频、图片下载

**并发度计算**：
- 总并发度 ≈ `video_concurrency * page_concurrency`
- 实际值接近 `video_concurrency * 1`（大多数视频只有单页）

## 限流与风控

### 漏桶算法

```
时间间隔 (ms) | 限制请求数
--------------|------------
    1000      |     5
```

表示每 1000 毫秒最多允许 5 个请求

### 风控检测

- 监控 HTTP 响应状态码
- 检测风控特征
- 自动终止并等待重试

## 配置系统

### 配置分类

1. **基本设置**
   - 绑定地址
   - 同步间隔
   - 文件命名模板

2. **B 站认证**
   - SESSDATA
   - bili_jct
   - DedeUserID

3. **视频质量**
   - 编码格式偏好
   - 视频质量范围
   - 音频质量范围

4. **弹幕渲染**
   - 字体、大小、颜色
   - 持续时间、位置
   - 透明度、描边

5. **高级设置**
   - 并发控制
   - 请求频率限制
   - 分块下载配置

### 配置持久化

- 自 2.6.0 版本开始，配置存储在数据库表中
- 支持实时生效（大部分配置）
- Web UI 提供可视化配置界面

## 技术亮点

1. **异步优先**：全程基于 Tokio 异步运行时
2. **类型安全**：Rust 强类型系统保证代码安全
3. **并发优化**：多级并发 + 限流控制
4. **错误恢复**：自动重试 + 风控处理
5. **可扩展性**：模块化设计，易于添加新功能
6. **用户友好**：Web UI + 智能默认配置
