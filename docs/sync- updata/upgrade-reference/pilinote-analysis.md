# PiliNote 项目架构分析

## 📊 执行摘要

本文档基于对 PiliNote 项目的深入分析，总结了当前架构的优缺点，并与 bili-sync 进行了对比分析，为后续升级提供参考。

## 🏗️ 架构概览

### 技术栈

- **后端**: Python + FastAPI
- **数据库**: SQLite (SQLAlchemy)
- **下载引擎**: yt-dlp
- **任务调度**: APScheduler
- **前端**: React + TypeScript + Vite

### 架构分层

```
FastAPI Application
├── Routers (API层)
│   ├── download.py      # 下载API（新旧系统兼容）
│   ├── favorites.py     # 收藏夹API
│   ├── watchlater.py    # 稍后再看API
│   └── queue.py         # 新队列系统API
├── Services (业务逻辑层)
│   ├── download_engine.py    # yt-dlp下载引擎
│   ├── download_manager.py   # 下载管理器（旧系统）
│   ├── scheduler_service.py  # 定时任务服务
│   └── queue/
│       ├── manager.py        # 队列管理器（新系统）
│       ├── scheduler.py      # 调度器服务
│       └── task.py           # 任务执行服务
├── Models (数据模型层)
│   ├── download.py      # 旧系统下载模型
│   ├── task.py          # 新系统任务模型
│   ├── scheduler.py     # 调度器模型
│   └── queue.py         # 队列模型
└── Config (配置层)
    └── config.py        # Pydantic配置
```

## ✅ 已有优势

### 1. 任务调度框架
- 使用 `APScheduler` 实现定时任务
- 支持 cookie 自动刷新（30分钟检查一次）
- 支持临时文件自动清理（1小时清理一次）
- 后台运行，不影响主流程

### 2. 视频源 API
- 收藏夹和稍后再看 API 已完整实现
- 使用 B 站原生 API，速度快（提升90%）
- 支持分页和无限滚动
- 统一的数据模型和认证依赖

### 3. 下载系统
- 新旧两套系统并存，功能完整
- 新系统支持批量任务调度（Scheduler）
- 支持多级队列（BACKLOG、PENDING、DOING、COMPLETE）
- 支持任务状态管理（7种状态）

### 4. 下载引擎
- 使用 yt-dlp，支持多种格式
- 自动检测工具路径（项目工具优先，系统工具回退）
- 支持暂停/继续/取消操作
- 支持进度回调
- 并发控制（最多3个并发）

### 5. 配置管理
- 使用 Pydantic Settings，类型安全
- 支持环境变量和 .env 文件
- 配置分类清晰（应用、数据库、认证、B站API）

## ❌ 主要缺失

### 1. 定时扫描视频源
- 没有类似 bili-sync 的定时扫描功能
- 无法自动发现收藏夹/稍后再看的新视频
- 需要手动添加下载任务

### 2. 增量更新机制
- 缺少 `latest_row_at` 类似的增量更新
- 每次都全量扫描，效率低
- 无法区分新旧视频

### 3. 自动订阅功能
- 没有一键订阅收藏夹/稍后再看
- 无法批量添加视频到下载列表
- 用户体验不够便捷

### 4. 限流控制
- 没有漏桶算法
- 容易触发 B 站风控
- 缺少请求频率控制

### 5. 风控检测
- 没有风控检测机制
- 下载失败后继续重试
- 可能导致账号被封

### 6. 分块下载
- 没有分块下载功能
- 大文件下载速度慢
- 无法充分利用带宽

### 7. CDN 智能排序
- 没有 CDN 排序功能
- 使用默认 CDN，速度不稳定
- 下载成功率较低

### 8. 自动重试
- 失败重试机制不完善
- 没有失败计数和阈值控制
- 无法自动放弃失败任务

### 9. 文件命名模板
- 没有文件命名模板功能
- 文件命名不够灵活
- 难以满足不同用户需求

### 10. 媒体服务器集成
- NFO 文件支持不完整
- 缺少 Emby/Jellyfin 完整集成
- 无法直接作为媒体库使用

## 🎯 PiliNote 优势

1. **开发效率高**: Python + FastAPI，开发速度快
2. **生态丰富**: 可使用 yt-dlp 等成熟工具
3. **架构清晰**: Router → Service → Model 三层架构
4. **用户体验**: Web UI 界面友好
5. **WebSocket支持**: 实时更新任务状态

## ⚠️ PiliNote 劣势

1. **两套系统并行**: 代码复杂度高，维护成本大
2. **缺少核心功能**:
   - ❌ 定时扫描视频源
   - ❌ 增量更新机制
   - ❌ 限流和风控
   - ❌ 分块下载
   - ❌ CDN智能排序
3. **性能瓶颈**:
   - Python 性能不如 Rust
   - 没有分块下载，大文件下载慢
   - 缺少缓存机制
4. **配置不够灵活**:
   - 没有文件命名模板
   - 没有运行时配置修改
5. **媒体服务器集成不完整**:
   - NFO 文件支持不完整
   - 缺少 Emby/Jellyfin 完整集成

## 🔍 关键问题

### 1. 系统状态不一致
- 两套系统并存，状态映射复杂
- `/api/download/list` 需要同时处理两套系统数据

### 2. 任务执行流程不清晰
- 新系统的任务执行流程较复杂
- TaskService、SchedulerService、QueueManager 职责有重叠

### 3. 缺少文档
- 没有架构设计文档
- 没有任务执行流程图
- 没有配置说明文档

### 4. 错误处理不完善
- 缺少统一的错误处理机制
- 部分异常只记录日志，不返回给用户

## 📋 改进建议

### 短期优化建议

1. **统一任务系统**:
   - 逐步迁移旧系统到新系统
   - 统一任务状态模型
   - 统一进度追踪机制

2. **完善定时任务**:
   - 添加视频源定时扫描功能
   - 实现增量更新机制
   - 添加任务重试机制

3. **增强限流控制**:
   - 实现漏桶算法
   - 添加风控检测
   - 添加下载限速功能

4. **优化下载性能**:
   - 实现分块下载
   - 添加 CDN 智能排序
   - 优化并发控制

### 中期优化建议

1. **重构配置系统**:
   - 支持运行时配置修改
   - 添加文件命名模板
   - 支持配置持久化

2. **完善媒体服务器集成**:
   - 完善 NFO 文件格式
   - 支持 Emby/Jellyfin 完整集成
   - 添加 UP 主头像支持

3. **增强缓存机制**:
   - 添加视频源数据缓存
   - 实现智能缓存失效
   - 减少不必要的 API 请求

### 长期优化建议

1. **架构重构**:
   - 统一任务系统
   - 优化服务层职责划分
   - 添加更多单元测试

2. **性能优化**:
   - 考虑关键路径使用 Rust 重写
   - 优化数据库查询
   - 添加性能监控

3. **功能扩展**:
   - 添加视频合集支持
   - 添加 UP 主投稿支持
   - 添加任务优先级管理

## 🎓 总结

PiliNote 项目在基础功能上已经比较完善，但在**自动化、智能化、性能优化**方面还有很大提升空间。通过借鉴 bili-sync 的优秀设计，可以实现：

1. **自动化**: 定时扫描、自动下载
2. **智能化**: 增量更新、智能筛选
3. **性能优化**: 分块下载、CDN排序、限流控制
4. **用户体验**: 一键订阅、文件命名模板、媒体服务器集成

建议优先实现**定时扫描和自动下载**功能，这是用户最核心的需求，也是提升用户体验的关键。
